# موافقات التسجيل وحجز البرامج

التنفيذ بتاريخ 21 سبتمبر 2026، وفق النصوص التي حددها صاحب المنصة. لا يمثل هذا التغيير بمفرده حكمًا قانونيًا باكتمال الامتثال.

## السلوك

- إنشاء الحساب: `is_terms` إلزامي، بالنص الخاص بالشروط والخصوصية ومعالجة بيانات الخدمات والشهادات، مع رابط لكل سياسة.
- `marketing_consent` اختياري، غير محدد مسبقًا، ويقبل boolean أو 0/1. الغياب أو 0 يسجل عدم الموافقة؛ لا يمنع إنشاء الحساب. خانة الإقرار بصحة البيانات السابقة ما زالت موجودة.
- `certificate_consent` إلزامي عند تقديم طلب حجز أي دورة أو برنامج، وفق تأكيد المستخدم أن الحكم يشمل جميع البرامج.
- مسارات الدفع بالتحويل أو تمارا تطلب موافقة الشهادة إذا لم توجد موافقة بنفس إصدار النص للبرنامج ونفس الاسم ورقم الهوية. يغطي هذا حالات التسجيل بواسطة الإدارة والحسابات القديمة.
- لا يتم توليد موافقة نيابة عن الطالب عند التسجيل الإداري، ولا إضافة موافقات تاريخية للحسابات القديمة.
- سجلات الشهادة توثق الموافقة الصريحة حتى إن فشلت محاولة الدفع لاحقًا؛ ليست دليلًا على نجاح الدفع أو إصدار شهادة.

## التخزين والعرض

جدول `consent_records` سجل مستقل للموافقات الثلاث؛ الجدول القديم `user_consent_logs` لا يُعدّل ولا تُنقل منه بيانات مفترضة. السجل الجديد يدعم قرار التسويق السلبي وموافقة مرتبطة ببرنامج، دون الحاجة لربط كل قرار بصفحة CMS.

يحفظ نوع القرار، القبول/عدم القبول، نص العبارة وإصدارها، وقت الخادم، IP الاتصال، المستخدم، والبرنامج عند الاقتضاء. الموافقة الأساسية تحفظ نسخة من صفحات الشروط والخصوصية المنشورة الموجودة وقت التسجيل، وموافقة الشهادة تحفظ الاسم والهوية واسم البرنامج وقت الموافقة. تعديل البيانات أو الصفحات بعد ذلك لا يعدل هذه النسخ.

التسجيل وإنشاء سجلي الموافقة الأساسية والتسويق في معاملة واحدة؛ فشل حفظ الموافقات يمنع بقاء حساب جديد بلا توثيق. طلب الحجز وتوثيق الشهادة كذلك في معاملة واحدة. الوقت مخزن حسب إعداد التطبيق، وواجهة الإدارة تعرض المنطقة الزمنية بجانبه. يجب ضبط البروكسي الموثوق على الاستضافة لتحديد IP العميل بشكل صحيح؛ لا يؤخذ IP من جسم الطلب.

تظهر أحدث 100 موافقة في صفحات تفاصيل المستخدم والطالب والتسجيل المعلق، مع النص والتاريخ وIP وإصدار السياسة. لا توجد واجهة لتعديل السجلات التاريخية. حذف المستخدم نهائيًا يحذف سجلاته وفق قيد قاعدة البيانات؛ يجب تحديد سياسة الاحتفاظ المؤسسية قبل أي إجراءات حذف نهائي.

هذا التغيير يحفظ اختيار التسويق، ولا ينفذ إرسالًا تسويقيًا. أي تكامل حملات لاحق يجب أن يستعلم عن أحدث قرار تسويق ويطبق الانسحاب؛ الإشعارات التشغيلية والتحقق ليست موافقة تسويق.

## تكامل التطبيق/الـAPI

`GET /api/v1/consents` يعيد النصوص وأسماء الحقول والإلزام وروابط السياسات وإصدار النص. جميع الاختيارات الافتراضية false.

في `POST /api/v1/auth/register`، أرسل `is_confirm_user: true` و`is_terms: true` بعد موافقة المستخدم على الإقرارين الإلزاميين، و`marketing_consent: true` فقط إذا اختاره المستخدم. غياب التسويق أو إرسال `false` يسجل عدم الموافقة ولا يمنع التسجيل. رفض أو غياب أي إقرار إلزامي يرجع `422`. تبقى بقية حقول التسجيل السابقة مطلوبة. يعيد `GET /api/v1/consents` الاختيارات الثلاثة؛ اربط كل اختيار باسم `field` وليس بترتيبه في القائمة.

في `POST /api/v1/student/enroll-program` أرسل `program_id` و`certificate_consent: true` بعد عرض النص وتحديده صراحة. مسارات دفع الطالب تقبل نفس الحقل عند الحاجة. غياب الموافقة المطلوبة يرجع 422 وحقل الخطأ `certificate_consent`.

يجب تحديث واجهة أي تطبيق منفصل يستهلك الـAPI قبل إطلاق اشتراط الموافقة للحجز والدفع. النصوص الحالية عربية؛ لا تُختلق ترجمة معتمدة.

## النشر والتحقق

1. أخذ النسخة الاحتياطية التشغيلية المعتادة وتشغيل migrations المعلقة على بيئة الاختبار ثم الإنتاج ضمن النشر: `php artisan migrate --force`.
2. تحديث التطبيق المنفصل إن وجد، ثم إعادة بناء القوالب: `php artisan view:cache`.
3. اختبار حساب جديد دون تسويق، وآخر بموافقة التسويق، وحجز دون/مع موافقة الشهادة، ودفع لبرنامج أضافته الإدارة، ثم مراجعة السجل.

اختبارات هذه الميزة: `php artisan test --compact tests/Feature/Auth/ConsentRecordingTest.php`. تستخدم اتصال SQLite بالذاكرة مخصصًا ولا تغير قاعدة بيانات المشروع أو تتصل بمزود الدفع أو الرسائل.
